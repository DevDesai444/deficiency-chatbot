is available.

Add a module-level helper `_build_field_hint` that safely constructs the field-level hint:

```python
def _build_field_hint(error_json: str | None, model_cls: type) -> str:
    """RELIABILITY-02: Build field-level reprompt from a pydantic ValidationError JSON string.
    
    parse_structured returns exc.json(indent=None) — a JSON-serialized error from pydantic.
    Attempt to extract per-field messages; fall back to generic hint if parsing fails.
    """
    _GENERIC_HINT = "send a JSON object matching this tool's schema exactly"
    if error_json is None:
        return _GENERIC_HINT
    try:
        errors = _json.loads(error_json)
        if not isinstance(errors, list) or len(errors) == 0:
            return _GENERIC_HINT
        lines = [f"Fix the following fields in {model_cls.__name__}:"]
        for e in errors:
            loc = ".".join(str(x) for x in e.get("loc", ["(unknown)"]))
            msg = e.get("msg", "invalid value")
            err_type = e.get("type", "")
            lines.append(f"  - Field '{loc}': {msg} [error_type={err_type}]")
        lines.append(f"Return ONLY valid JSON matching the {model_cls.__name__} schema.")
        return "\n".join(lines)
    except Exception:
        return _GENERIC_HINT
```

Note: this approach avoids importing `format_field_level_reprompt` directly (which
requires a real `ValidationError` object) and instead parses the JSON string that
parse_structured already produced — cleaner integration with the existing flow. The
`format_field_level_reprompt` function in reliability.py remains the canonical
implementation for direct ValidationError usage (e.g., in Plan 05's verify loop).
Both functions produce field-level messages; this adapter bridges the existing
parse_structured→error-string flow to the RELIABILITY-02 contract.
