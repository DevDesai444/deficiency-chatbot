## 1. System Classification

**System Type:** Hybrid — Autonomous agentic verify/challenge loop with a Structured-Extraction reliability core

**Description:**
Phase 6 stands up the reasoning/verification model the β verifier runs on — NVIDIA Nemotron-Super-49B-v1.5, self-hosted on the company's Databricks (`aip-amn-dev`) via self-managed vLLM alongside Llama 3.3 70B + Qwen MoE — and a shared weak-model reliability layer that both the review tool-call path and `structured.py` consume. Given a candidate deficiency (claim + cited source span + the rule it allegedly violates), the verifier returns a machine-parsable `VERDICT` (`KEEP|DOWNGRADE` + confidence + rationale + grounding_span). "Good" is: the model is production-wired on-prem with **no external LLM API ever reachable**, it clears the pre-registered D-06 two-dimensional bar (≥98% VERDICT conformance post-repair in both thinking modes **and** ≥80% discrimination on the known-good/known-bad probe split), and weak-model tool-args parse reliably (server-side guided decoding + field-level errors + lossless coercion + typed `ParseFailed`) so real findings are never dropped to malformed JSON. Phase 6 proves the model + reliability substrate; Phase 7 builds the verifier sub-agents and never-drop→KEEP orchestration on top.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. **External-model leakage of regulated pharma data.** A config-drift model-id (`databricks-claude-*` / `-gpt-5-*` / `-gemini-*`) reaches the client boundary and regulated submission content is sent off-prem. The D-16 allow-list guard must BLOCK/fail-loud — this is a data-residency incident, never a silent downgrade.
2. **A real deficiency silently dropped to a malformed tool-arg.** A weak model (Llama/Qwen) returns a verdict whose args don't parse (quoted numbers, single-key wrappers, off-enum tokens) and the finding disappears before a human sees it. The guided-decode → coercion → field-level-retry → typed-`ParseFailed` stack must surface the failure, never lose it.
3. **A fabricated verdict on parse failure.** The reliability layer invents/defaults a `KEEP`/`DOWNGRADE` when it couldn't actually read the model — conflating "verifier said keep" with "we couldn't read the verifier" and destroying the fallback telemetry. Contract is `VERDICT` XOR `ParseFailed`; the caller (Phase 7) decides parse-failure→KEEP.
4. **A syntactically-perfect but non-discriminating verifier.** A constant-KEEP (or blanket-DOWNGRADE) model passes conformance with perfect JSON while doing no real review — KEEPing the ~100-FP over-emit at the same rate as the 5 matched-GT findings. The D-06b discrimination bar + constant-verdict tripwire must fail this even at 100% parse rate.
5. **Advertised schema loosened to "recover" args.** Coercion quietly widens what the tool accepts (or guesses an enum) to make malformed args pass — trading precision for parse rate. SC4 requires the advertised schema stay unchanged; only lossless, information-preserving coercions are allowed and enums are never guessed.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Pharmaceutical regulatory affairs — FDA/ICH drug-submission (NDA/ANDA) compliance review.

**User Population:** Regulatory analysts and CMC/quality reviewers preparing or auditing a drug-submission document set before it goes to FDA. In this phase the direct "consumer" of the AI output is the review pipeline itself: the verifier model gates each candidate deficiency the deterministic recall engine emits. The human in the loop is a regulatory analyst who trusts DefPredict to surface every real FDA/ICH gap and nothing else, each proven by the exact passage.

**Stakes Level:** Critical.

**Output Consequence:** A verifier verdict decides whether a candidate deficiency (claim + cited source span + the rule it allegedly violates) is KEPT and shown to the analyst or DOWNGRADED and suppressed. A wrong DOWNGRADE drops a real FDA/ICH deficiency → a genuine compliance gap ships unflagged in a submission (risk of a Complete Response Letter, refuse-to-receive, or a cGMP finding downstream — 21 CFR 314.110). A wrong KEEP surfaces a hallucinated or mis-cited deficiency → the analyst wastes review time chasing a non-issue and loses trust in the tool ("blabber"). Both directions are costly in a regulated pharma context; the product's whole value is recall + precision with verbatim grounding.

### What Domain Experts Evaluate Against

These are the questions an FDA/ICH reviewer would actually ask of each KEEP/DOWNGRADE verdict — expressed in review language, not AI jargon. They are the source rubric ingredients the eval-planner turns into measurable dimensions in Section 5.

```
Dimension: Governing-text grounding (is the cited passage the text that actually decides this?)
Good: A KEEP rests on a verbatim span from the submission that genuinely evidences the gap; the grounding_span is copied from the source, not paraphrased, and is the passage a reviewer would themselves point to.
Bad: The verdict is grounded to a plausible-but-wrong span (right document, adjacent/unrelated sentence) or to a paraphrase the model wrote rather than a quote from the document.
Stakes: Critical
Source: DefPredict grounding contract (no finding without a verbatim doc→section→span anchor); FDARxBench "fine-grained provenance" requirement co-defined with FDA regulatory assessors.
```

```
Dimension: Correct rule mapping (does the finding cite the specific rule it truly violates?)
Good: The alleged violation maps to the governing citation at the right granularity — e.g. a stability gap → ICH Q1A/21 CFR 211.166; an analytical-method validation gap → ICH Q2; an impurities/specification gap → ICH Q3A–D / Q6A; an e-records gap → 21 CFR Part 11. A KEEP is upheld only when the rule genuinely governs the cited text.
Bad: The finding cites a real-sounding but wrong or over-broad rule (e.g. tagging a labeling issue to a manufacturing section), or asserts a violation of a rule the cited passage does not actually implicate.
Stakes: Critical
Source: 21 CFR Title 21 (211 cGMP, 314 NDA/ANDA, 320 BA/BE, Part 11) + ICH Q/S/E/M guideline scope; CRL practice — deficiencies are enumerated against specific governing provisions (21 CFR 314.110).
```

```
Dimension: Justified DOWNGRADE (is a rejection reasoned from absence-of-violation, not model laziness?)
Good: A DOWNGRADE is upheld because the reviewer, reading the cited span against the rule, agrees no real violation is present (the requirement is met, the reference resolves, the value is compliant) — i.e. correct, defensible abstention.
Bad: A DOWNGRADE that drops a real deficiency because the model under-reasoned, hit the wrong thinking-mode, or defaulted to "looks fine." Equally: a rubber-stamp KEEP with a generic rationale that never engaged the span (a constant-verdict model can pass syntax while doing no review).
Stakes: Critical
Source: FDARxBench "reliable abstention on unanswerable questions"; DefPredict recall mandate (find ALL real deficiencies — a false DOWNGRADE is a missed finding).
```

```
Dimension: Verdict reliability under thinking-mode (does the same candidate get the same verdict with reasoning on vs off?)
Good: A candidate receives a stable, well-reasoned verdict whether the reasoning trace is on or off; reasoning-ON produces a clearer rationale but does not flip a defensible KEEP to a spurious DOWNGRADE (or vice-versa).
Bad: The verdict is inconsistent between `detailed thinking on` and `off` for the same candidate — a reviewer cannot trust a gate whose answer depends on an internal toggle.
Stakes: High
Source: 06-CONTEXT D-06/D-18 (both modes must clear the pass bar separately; the split is measured, not assumed); regulatory-review reproducibility expectation.
```

```
Dimension: Discrimination between real and planted-false deficiencies
Good: Across a mixed set of known-real and known-false candidates, the verifier separates them — KEEPing the matched-ground-truth deficiencies and DOWNGRADing the false over-emitted ones.
Bad: The verifier fails to discriminate — e.g. KEEPs the false-positive over-emit at the same rate as the real findings, or blanket-DOWNGRADEs to look "precise." Perfect JSON conformance with no discrimination is a fail.
Stakes: Critical
Source: 06-CONTEXT D-05/D-06 two-dimensional pass bar (≥98% conformance AND ≥80% correct on the known-good/known-bad split of the 115 real β candidates, matched-GT vs 100-FP over-emit).
```

### Known Failure Modes in This Domain

These are the regulatory-review-specific ways a verifier goes wrong — the failure surface the eval and guardrails must catch, not generic "hallucination."

- **Rule mis-citation.** The verdict names a real but wrong FDA/ICH provision (labeling issue tagged to a manufacturing section, stability gap tagged to the wrong ICH Q-series). The finding looks authoritative but a reviewer would reject the citation — corrodes trust even when a gap genuinely exists.
- **Plausible-but-wrong grounding span.** The verdict cites the right document but the wrong sentence — an adjacent or thematically-similar passage that does not actually evidence the deficiency. The hardest false-positive to catch because the citation superficially "checks out."
- **False-positive over-emit (the mvr1381 100-FP tail).** The recall engine emits ~100 false candidates alongside the 5 matched-ground-truth ones; a verifier that KEEPs indiscriminately floods the analyst with non-issues ("blabber"), the exact precision failure the product exists to prevent.
- **Silently dropped findings via malformed tool-args.** A weak open-weights model (Llama/Qwen) returns a KEEP/DOWNGRADE whose tool-call args don't parse (quoted numbers, single-key wrappers, off-enum verdict tokens) and the finding is lost before a human ever sees it — a real deficiency disappears not because it was reviewed away but because the JSON broke. This is the specific weak-model reliability failure this phase hardens (RELIABILITY-01/02/03).
- **Verdict inconsistency across reasoning mode.** The same candidate flips KEEP↔DOWNGRADE depending on `detailed thinking on/off`, making the gate non-reproducible.

### Regulatory / Compliance Context

- **On-prem data-residency (HARD, itself a compliance stake):** regulated pharma submission content must NEVER leave the company's infrastructure — no external LLM API (Claude/GPT/Gemini) is ever called. The verifier runs on self-hosted open-weights models (Nemotron-Super-49B, Llama 3.3 70B, Qwen MoE) on Databricks `aip-amn-dev`. This is not a preference but a confidentiality/security requirement; a config-drift call to an external model is a critical failure mode (guarded by the D-16 on-prem allow-list). Relevant framing: 21 CFR Part 11 (electronic records/data integrity) and general pharma trade-secret confidentiality of unpublished submission data.
- **Governing rulebook the findings are measured against:** 21 CFR Title 21 — Part 211 (cGMP), Part 314 (NDA/ANDA, incl. §314.110 Complete Response Letter deficiency enumeration), Part 320 (BA/BE), Part 11 (e-records); and the ICH Q/S/E/M guidelines (Q1 stability, Q2 method validation, Q3A–D impurities, Q6A specifications, Q8–Q12). ICH content carries a public license conditioned on acknowledging ICH copyright — attribution must travel with each ICH-cited finding.
- **Reviewer-grade evidence standard:** FDA deficiencies are enumerated against specific governing provisions with supporting text; the product mirrors this — every KEEP must carry the rule + verbatim span, the same evidentiary bar a CRL applies.

## 2. Framework Decision

**Selected Framework:** Self-managed vLLM (serving) + hand-rolled tool loop on `openai` with server-side guided decoding (vLLM `guided_json`) — **no new agent framework**

**Version:** vLLM (self-managed on Databricks GPU serving) · `openai>=2.40` · `pydantic>=2.7` · `json-repair>=0.30` (all already pinned in `pyproject.toml`)

**Rationale:**
The HARD on-prem/privacy constraint (Llama + Qwen + Nemotron self-hosted on Databricks `aip-amn-dev`; **no external LLM API — Claude/GPT/Gemini — ever called**) eliminates every provider-native SDK (OpenAI Agents SDK, Claude Agent SDK, Google ADK). The project's "build your own thin loop, keep control of grounding/verification/compaction" thesis, plus the already-hardened `structured.py` (L1–L6 + `ParseFailed`) and `registry.dispatch` (`ToolRejected`) assets, eliminate every heavy orchestration framework (LangChain, LangGraph, CrewAI, AutoGen, LlamaIndex, Haystack). Phase 6 is **model serving + a shared reliability layer**, not agent orchestration: the correct stack is self-managed vLLM (D-03 — for `guided_json`, custom tool-parser flag, and `detailed thinking on/off` controls that Databricks managed Provisioned Throughput does not expose) fronted by the existing OpenAI-compatible client, with reliability via `guided_json` → native tool-parser → strict lossless coercion → field-level error + bounded retry → typed `ParseFailed` sentinel (D-08..D-15). This **validates the already-locked stack** — no framework adoption is warranted.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| OpenAI Agents SDK / Claude Agent SDK / Google ADK | Provider-native — cannot drive on-prem Llama/Qwen/Nemotron; on-prem constraint forbids any external LLM API. |
| LangChain / LangGraph / CrewAI / AutoGen / LlamaIndex / Haystack | Heavy orchestration abstractions fight the bespoke grounding/verification/compaction that is the project's moat; would require rewriting hardened `structured.py`/`registry.dispatch`. AutoGen already flagged dead-weight for removal. |
| Databricks managed Provisioned Throughput (serving) | Does not expose vLLM-native `guided_json` / custom tool-parser / `detailed thinking on/off`; may not support Nemotron's NAS-pruned Llama arch (D-03). |
| **PydanticAI 2.x** (typed tool/output layer over the same vLLM endpoints) | **Not ruled out — held as fallback.** Adopt only if hand-rolled per-field VERDICT validation proves too noisy across Llama/Qwen/Nemotron; reuses pydantic v2, stays model-agnostic and on-prem, adds no vendor lock-in. Do NOT adopt if it forces a `structured.py` rewrite. |

**Vendor Lock-In Accepted:** No — the stack is model-agnostic and fully on-prem (self-managed vLLM behind an OpenAI-compatible client). The only "lock-in" is to open-weights + open-source serving, which is the explicit privacy requirement.

**C) Runtime capability probe (D-09 — mirrors the existing `response_format` BadRequestError→degrade in client.py):**
```python
# Detect ONCE per endpoint, cache the result. Fail-safe: any error ⇒ assume unsupported, fall through.
_guided_cache: dict[str, bool] = {}

def supports_guided_json(client: OpenAI, model: str) -> bool:
    if model in _guided_cache:
        return _guided_cache[model]
    try:
        client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": "ping"}],
            max_tokens=1,
            extra_body={"structured_outputs": {"json": {"type": "object"}}},
        )
        _guided_cache[model] = True
    except BadRequestError:
        _guided_cache[model] = False        # endpoint rejected it → degrade to native tool-parser
    except Exception:
        _guided_cache[model] = False        # fail-safe: never block the real call on a probe error
    return _guided_cache[model]
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `extra_body={"structured_outputs": {"json": schema}}` | vLLM's OpenAI-compat channel for server-side constrained JSON decoding (legacy alias `guided_json`) | On EVERY tool-call turn + VERDICT when the endpoint is probed-supported (D-08) |
| `--tool-call-parser llama_nemotron_json` (+ `--tool-parser-plugin`) | Nemotron's DPO tool-call format parser, shipped as a plugin file in the model repo | Set at Nemotron launch; different per model family (D-08) |
| `structured_outputs` backend (`xgrammar` / `guidance` / `outlines`, default `auto`) | The constrained-decoding engine vLLM selects to enforce the schema | Pin only if `auto` picks a backend that rejects a schema feature (e.g. `pattern`) |
| Reasoning toggle via **system prompt** | `detailed thinking on` / `detailed thinking off` (v1) or `/no_think` (v1.5 card) — NO `--reasoning-parser` needed | Set per call for D-18 on/off latency+cost split; the exact string is a probe target (version-dependent) |
| `tool_schema_for_databricks()` (existing) | Inlines `$ref`, strips `pattern`, forces `additionalProperties:false` — already produces a vLLM-legal schema | Reuse verbatim to build the `guided_json` schema; do NOT hand-write schemas |

### Common Pitfalls
1. **Reusing one `--tool-call-parser` across model families.** Nemotron's `llama_nemotron_json` is NOT interchangeable with Llama-3.3's `llama3_json` or Qwen's parser. Wrong parser → tool_calls silently return as prose in `content`, not structured `tool_calls` (D-08 is per-endpoint).
2. **Assuming the reasoning-toggle string is stable across versions.** v1 used `detailed thinking on/off`; the v1.5 card documents `/no_think`. Hardcoding the wrong token silently leaves the model in the wrong mode (blows the D-18 cost split and the D-06 parse bar). Probe both, record which one actually flips token counts.
3. **Treating `guided_json`/`structured_outputs` as free precision.** Guided decoding guarantees *syntactic* schema conformance, NOT semantic correctness — a constant-KEEP model still passes syntax. This is exactly why D-06 pairs conformance with a discrimination bar; do not let the guided-decode green light stand in for verdict quality.
4. **Sending `pattern`/`anyOf[X,null]` in the guided schema.** Some vLLM backends (and the existing Databricks strict path) reject `pattern` and choke on nullable `anyOf`. `tool_schema_for_databricks()` already sanitizes these — route every guided schema through it, never `model.model_json_schema()` raw.
5. **Coercing an enum.** The VERDICT `verdict` field is `KEEP|DOWNGRADE`. D-11 forbids guessing enum values — a token that isn't exactly one of them FAILS to typed `ParseFailed`, it is never "snapped" to the nearest. Numeric-string→number and `'true'/'false'`→bool are the ONLY lossless coercions allowed; log every rejected near-miss (structlog counter) rather than loosening.
6. **Probing capability on the hot path.** The D-09 probe must be detect-once-and-cache per endpoint. Re-probing every call doubles request volume and pollutes the D-18 latency numbers.

## 4. Implementation Guidance

**Model Configuration:**

| Role | Model (served-name) | Lineage tag (D-17) | Params | Notes |
|------|--------------------|--------------------|--------|-------|
| `verifier_model` | `nemotron-super-49b-v1_5` | `nemotron-on-llama` | ~50B | Verify/challenge + hard reasoning. Self-managed vLLM (D-03). |
| `detector_model` (recall/emit) | `databricks-meta-llama-3-3-70b-instruct` | `llama` | 70B | β recall is deterministic; Llama used for interpretive tasks. |
| `moderator_model` (rescue) | `databricks-meta-llama-3-3-70b-instruct` | `llama` | 70B | L5 schema-repair (existing). |
| alt worker/triage | `databricks-qwen35-122b-a10b` | `qwen` | MoE | Decorrelated second opinion (Phase 7). |

Params (verifier VERDICT calls):
- **temperature:** `0.0` (greedy) for reasoning **OFF** confirm passes; `0.6` + `top_p 0.95` for reasoning **ON** (per model card). Record BOTH per D-18.
- **max_tokens:** explicit, bounded. VERDICT is tiny → `256` OFF; ON needs headroom for the reasoning trace before the JSON → `2048` (still capped by `s.max_tokens_ceiling`). Never unbounded (Pitfall: reasoning-ON without a ceiling burns the budget on think tokens).
- **reasoning toggle:** set in the **system prompt** (`detailed thinking on|off` / `/no_think`), NOT a launch flag — so one warm endpoint serves both modes.

**Core Pattern:** (verify tool-call turn, guided-decoded, single bounded corrective retry — D-08/D-10/D-13)
```python
def verified_tool_turn(messages, tools, model, verdict_schema):
    client = get_client()                                    # on-prem guard already applied (D-16)
    extra = {}
    if supports_guided_json(client, model):                  # D-09 cached probe
        extra = {"structured_outputs": {"json": verdict_schema}}   # D-08 guided decode

    turn = chat_completion_tools(messages, tools, model=model, temperature=0.0,
                                 max_tokens=256, tool_choice="auto", extra_body=extra or None)

    verdict, failure = coerce_and_validate(turn, VERDICT)    # native parse → strict lossless coercion → pydantic
    if failure and retries_left(budget):                     # D-13 cap=1, budget-counted
        messages.append(field_level_reprompt(failure))       # RELIABILITY-02: name field + expected type
        turn = chat_completion_tools(messages, tools, model=model, temperature=0.0,
                                     max_tokens=256, extra_body=extra or None)
        verdict, failure = coerce_and_validate(turn, VERDICT)

    return verdict, failure                                   # VERDICT xor ParseFailed — never fabricate (D-12)
```
> `chat_completion_tools` must gain an `extra_body` passthrough param — that is the ONE client.py change the pattern needs, alongside the D-16 guard in `get_client`.

**Tool Use:** All 7 review tools + VERDICT get a `guided_json` schema built via the existing `tool_schema_for_databricks(model_cls)` (D-08). The advertised tool schema is unchanged (SC4) — guided decoding constrains the *arg object*, it does not alter what the model is told the tool accepts. When `supports_guided_json` is False, the native `--tool-call-parser` carries the turn and the coercion/retry stack catches malformed args.

**State Management:** Stateless per verdict — no framework session store. The message list is the state, echoed back verbatim via `ChatTurn.raw_message` (Pitfall 10 in client.py: never hand-reconstruct the assistant message / mismatch `tool_call_id`). The capability-probe cache (`_guided_cache`) and per-mode latency/token counters (D-18) are the only cross-call state; both live in `reliability.py` process memory, keyed by served-model-name.

**Context Window Strategy:** Nemotron launched at `--max-model-len 65536`. Verify is per-candidate and narrow (one cited span + one rule + the VERDICT), so context pressure is low — no compaction needed in Phase 6 (compaction/prefix-cache is deferred to Phase 8, COST-01/02/03). Guardrail: reasoning-ON traces can be long; the `max_tokens` ceiling + truncation-retry already in `structured.py` L2 bounds the completion side, and the input side stays small by construction (do NOT stuff whole documents — re-open by identifier, per the just-in-time retrieval design).

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

The minimal `VERDICT` arg-model (D-07) lives in `src/schemas/llm.py` next to `ParseFailed`. It is BOTH the probe's assertion target and the concrete schema guided-decode + coercion protect. Phase 7 **extends** it (add fields), never redefines.

```python
from enum import Enum
from pydantic import BaseModel, Field

class Verdict(str, Enum):
    KEEP = "KEEP"
    DOWNGRADE = "DOWNGRADE"

class VERDICT(BaseModel):
    verdict: Verdict                                  # enum — NEVER coerced (D-11); off-value ⇒ ParseFailed
    confidence: float = Field(ge=0.0, le=1.0)         # coercible: numeric-string→float (lossless)
    rationale: str                                    # why keep/downgrade
    grounding_span: str                               # verbatim cited span the verdict rests on
```

**How the stack integrates it (defense-in-depth, D-10 — generalizes `structured.py` L1–L6, does not rewrite it):**
1. **Guided decode (server):** `guided_schema = tool_schema_for_databricks(VERDICT)` → `extra_body={"structured_outputs": {"json": guided_schema}}` when the endpoint is probed-supported (D-09). This is L1 for the tool-call path — the analogue of `build_response_format` in `structured.py`.
2. **Native tool-parser:** `--tool-call-parser llama_nemotron_json` returns structured `tool_calls`; args are `json.loads`'d.
3. **Strict lossless coercion (D-11):** BEFORE `VERDICT.model_validate`, apply the allow-list: numeric-string→number, `'true'/'false'`→bool, single-key wrapper unwrap (`{"VERDICT": {...}}` → `{...}` only when the key matches). Enums are pass-through only. Every rejected near-miss increments a structlog counter.
4. **Pydantic validate:** `VERDICT.model_validate(coerced)` — reuse `structured.py:parse_structured`'s json-repair→validate path.
5. **Field-level error + bounded retry (RELIABILITY-02, D-13):** on `ValidationError`, emit a re-prompt naming the failing field and its expected type (not the generic `hint`); cap = 1, budget-counted.
6. **Typed sentinel (D-12):** exhausted → return `ParseFailed`, never a fabricated verdict. Caller (Phase 7) decides parse-failure→KEEP.

**Retry logic:** exactly **1** corrective retry (`structured_output_max_repair_calls`-style config knob, default 1). Log per attempt: `repair_layer` (none/pre/post), which field failed, whether coercion fired, and the near-miss token if any. Surface to caller only after the cap is hit — as `ParseFailed`, so the never-drop→KEEP telemetry stays honest (the Phase-3 hidden-fallback lesson).

### Async-First Design

The current `client.py` path is **synchronous** (`client.chat.completions.create`); there is no event loop in the drive-loop today, so `asyncio.run()` reentry is not yet a risk. Keep it sync for Phase 6 — the verify loop is per-candidate and the reliability stack is CPU-cheap. When Phase 7 fans out verifier sub-agents:
- Use `openai.AsyncOpenAI` + `asyncio.gather` for the fan-out, NOT threads (the openai client is not thread-safe to share cavalierly; async avoids the GIL contention on JSON parsing).
- **The one mistake:** calling `asyncio.run()` from inside an already-running loop (e.g. a FastAPI async handler) → `RuntimeError: asyncio.run() cannot be called from a running event loop`. Inside a handler, `await` the coroutine directly.
- **Stream vs await:** for the CLI UX (live progress, "Claude in the terminal" feel) stream *reasoning traces* token-by-token; but **await the full completion before validating** the VERDICT — you cannot pydantic-validate a half-streamed JSON object, and guided decoding only guarantees the schema at end-of-generation.

### Prompt Engineering Discipline

- **System vs. user separation:** the reasoning toggle (`detailed thinking on|off` / `/no_think`) and the verifier role instruction go in the **system** prompt; the candidate under review (cited span + rule + claim) goes in the **user** prompt. Keeping the toggle out of the user turn means it stays a stable, cacheable prefix (Phase 8 prefix-cache lever).
- **Few-shot:** for the KEEP/DOWNGRADE decision, inline 1–2 canonical examples (one clear KEEP, one clear DOWNGRADE) drawn from the D-05 known-good/known-bad split — do NOT dynamically retrieve; the decision rubric is small and stable, retrieval adds latency and non-determinism to a verification gate.
- **max_tokens is always explicit** (256 OFF / 2048 ON, capped by `max_tokens_ceiling`). Unbounded generation on reasoning-ON is how a single hard refutation eats the run budget.

### Context Window Management

This is a Hybrid **autonomous** system, so the relevant lever is *just-in-time retrieval*, not RAG chunking or conversation summarisation:
- **Do not preload** documents into the verify context — re-open the exact cited span by identifier (the existing tool-based navigation). Input stays small by construction, well under the 65 K window.
- **Completion side:** reasoning-ON traces are the only real context risk. `structured.py` L2 truncation-retry (finish_reason `length` → 2× max_tokens, capped) already handles a trace that runs past the budget; reuse it for the verify path.
- **Compaction / prefix-cache / cheap-triage cost governance is explicitly Phase 8 (COST-01/02/03)** — do not build it here.

### Cost and Latency Budget

- **Per-call:** self-hosted → the cost is *standing GPU time*, not per-token API billing (D-04 accepts an always-warm `GPU_XLARGE_8` endpoint). The budget lever is therefore **latency/throughput per verdict**, not dollars-per-token. Record, per D-18, for BOTH modes: wall-latency, prompt_tokens, completion_tokens (from `ChatTurn.usage`; flag `usage_present=False` as an estimate).
- **The on/off split IS the cost model:** reasoning-OFF greedy confirm is the cheap default; reasoning-ON is reserved for hard refutations. Phase 6 only *measures* the two costs (D-18); Phase 7 designs the escalation trigger from that data.
- **Caching:** exact-match + semantic caching and the stable-prefix prompt cache are Phase 8. For Phase 6, the only cache is the D-09 per-endpoint capability probe (detect-once) — cheap, correctness-preserving, and it keeps the D-18 latency numbers clean.
- **Cheaper models for sub-tasks:** verify is the expensive reasoning step; keep recall deterministic (β) and route triage/worker fan-out to Llama-70B / Qwen, escalating to Nemotron only for confirm/refute. The lineage tags (D-17) ensure a Llama-lineage verifier never "independently" rubber-stamps a Llama-produced candidate.

## 5. Evaluation Strategy

> Grounds directly on the **already pre-registered D-06 two-dimensional pass bar** in `06-CONTEXT.md`. This section does NOT invent a parallel bar — it turns the Section-1b rubric ingredients into the measurable dimensions that back D-06 (conformance + discrimination), plus the D-14 reliability-delta and D-18 thinking-mode split. All metrics are **code-based** (probe replay + rate diff) — no external LLM judge, because an external judge would call an off-prem model and violate MODEL-01. Where a semantic-quality judgment is unavoidable it is a **human** regulatory-reviewer step on the D-05 labels, never an external API.

### Dimensions

| # | Dimension | Rubric (Pass/Fail) | Measurement Approach | Priority | Ties to |
|---|-----------|--------------------|----------------------|----------|---------|
| E1 | **VERDICT conformance (D-06a)** | PASS: a machine-parsable `VERDICT` (valid `verdict∈{KEEP,DOWNGRADE}`, `confidence∈[0,1]`, `rationale`, `grounding_span`) is recovered post-repair on **≥98%** of the 115 probes — measured with `detailed thinking` **ON and OFF each separately**, PLUS the single tool-call round-trip probe passes. FAIL: any mode falls below 98%, or the round-trip probe returns prose-in-content instead of a structured tool_call. | **Code** — replay probe suite through `src/llm/reliability.py`; assert parse success; DeepEval custom metric (`conformance_rate`) per mode. | **Critical** | MODEL-02, RELIABILITY-01, D-06a |
| E2 | **Discrimination: real vs planted-false (D-06b)** | PASS: on the known-good/known-bad split (5 matched-GT [A-09/A-11/B-01/C-01/C-06] KEEP vs the ~100-FP over-emit DOWNGRADE), the verifier separates them at **≥80% correct on knowns**, each thinking-mode separately. FAIL: <80%, OR a constant-verdict signature (KEEPs the FP tail at the same rate as matched-GT / blanket-DOWNGRADEs) even with perfect JSON. | **Code** — compare emitted `verdict` to the D-05 matched-GT/FP labels; DeepEval metric (`discrimination_accuracy`) + a constant-verdict guard (fail if one verdict value ≥95% of outputs). | **Critical** | MODEL-02, D-06b, VERIFY-01 (pre-wire) |
| E3 | **Malformed-arg reliability delta (D-14)** | PASS: post-hardening **pre-repair malformed-arg rate** and **post-repair residual** are **arithmetically lower** than the pinned Phase-3 baseline numbers (Llama v2/v3 rates + Qwen 4/5 post-repair failures), replayed on the same probe suite. FAIL: rate not reduced, or reduced only by loosening the advertised schema (SC4 violated). | **Code** — replay same suite pre/post through `reliability.py`; diff the D-TEL4 `repair_layer` counters; DeepEval assertion `residual_post < baseline_post`. | **Critical** | RELIABILITY-01/02/03, D-14 |
| E4 | **Thinking-mode verdict stability (D-18)** | PASS: for the same candidate, the verdict does not flip KEEP↔DOWNGRADE between `on` and `off` on the matched-GT set (defensible-KEEP stays KEEP); any flip is logged with both rationales for reviewer adjudication. FAIL: unexplained flips on matched-GT candidates. | **Code** for the flip-count (diff ON vs OFF verdict arrays) + **Human** (regulatory reviewer) adjudicates whether a flip was defensible. | **High** | D-06 (both modes separately), D-18 |
| E5 | **Typed-failure honesty (D-12)** | PASS: on exhausted retries the layer returns a typed `ParseFailed` and **never fabricates a verdict**; every probe result is `VERDICT` XOR `ParseFailed`, and the fallback path is counted (not hidden). FAIL: any synthesized/defaulted verdict on a parse failure, or a silent drop. | **Code** — assert return type is the XOR contract; assert a `ParseFailed` counter increments; unit test the never-fabricate invariant. | **Critical** | RELIABILITY-02, D-12 |

FAIL: paraphrased/adjacent-wrong span, or real-but-wrong/over-broad rule. | **Human** — senior regulatory/CMC reviewer adjudicates a sampled subset of the matched-GT KEEPs (calibration only; sets the semantic ceiling the code metrics cannot see). If an on-prem judge is ever added it must (a) run on Nemotron/Llama/Qwen only, (b) be a *different lineage* than the model under test (D-17), and (c) be calibrated against the E6 human labels first.

## 7. Production Monitoring

**Tracing Tool:** **`structlog` (existing, on-prem)** — extended with the Phase-6 counters. This is the already-present on-prem tracing substrate (D-TEL4 `repair_layer` counters, D-11 near-miss counters, D-18 per-mode latency/token counters); it stays fully inside the company infra, satisfying MODEL-01. Arize Phoenix (GSD default, self-hostable via OpenTelemetry, on-prem-compatible) is deferred to Phase 7 when verifier fan-out makes span-level trace visualization worth the added collector — Phase 6's need is counters, which `structlog` already covers.

**Key Metrics to Track:**
1. **Conformance rate per thinking-mode (D-06a):** % of verify turns yielding a machine-parsable `VERDICT` post-repair, `on` and `off` tracked separately (target ≥98%).
2. **Discrimination accuracy (D-06b):** % correct on the known-good/known-bad split when the probe suite is re-run (target ≥80%); plus a constant-verdict ratio (share of the majority verdict) as a gameability tripwire.
3. **Pre-repair malformed-arg rate + post-repair residual (D-14):** split by `repair_layer` (none/pre/post) and model family — the D-TEL4 counters, diffed against the pinned Phase-3 baseline.
4. **Per-mode latency + token cost (D-18):** wall-latency, `prompt_tokens`, `completion_tokens` from `ChatTurn.usage` for `on` vs `off` (flag `usage_present=False` as estimated) — this IS the cost data Phase 7's escalation trigger is designed from.
5. **`ParseFailed` / typed-failure rate (D-12):** how often the verify layer returns the sentinel — the honest "the fallback carried the loop" signal that must stay visible.

**Alert Thresholds:**
- **PAGE (critical):** any allow-list guard trip (D-16) — an external-model id reached the client boundary; treat as a data-residency incident.
- **PAGE:** conformance rate drops below 98% in either mode, OR post-repair residual malformed-arg rate rises to ≥ the pinned Phase-3 baseline (findings are silently dropping).
- **ALERT:** discrimination accuracy below 80%, OR a constant-verdict signature (majority verdict ≥95%) — the verifier stopped reviewing.
- **ALERT:** reasoning-ON per-verdict latency/token cost drifts >2× its recorded D-18 baseline (budget regression before Phase-7 escalation is even wired).

**Smart Sampling Strategy:**
- **Full capture (no sampling)** for the catastrophic signals: allow-list trips, `ParseFailed` events, and rejected enum near-misses — each is rare and each represents a potential dropped finding or residency breach.
- **Signal-weighted sampling** for human reviewer adjudication (E4/E6): weight toward (a) candidates whose verdict **flipped** between thinking modes, (b) low-`confidence` KEEPs near the decision boundary, (c) any candidate that required a corrective retry, and (d) matched-GT candidates that were DOWNGRADED (a would-be missed real deficiency — the highest-stakes error). Route these to the regulatory reviewer, not an LLM.
