## Decisions Made

See `key-decisions` in frontmatter above for the full list. Highlights:

- **Anchor matching is scoped to `Fault.evidence` alone**, not the full `finding_text()` concatenation the plan's `<action>` text describes for `finding_text()` itself. This mirrors `agents.detection.verify`'s real, already-shipped `_anchored(f.evidence, corpus)` precedent (never anchors off title/detail) and is fully compatible with the plan's own two illustrative examples (both frame matching in terms of "evidence contains X") and the required acceptance-criteria script (which only ever populates the `evidence` field in its test fault dict).
- **Numeric anchor-token floor raised from 3 to 4 characters**, matching `verify.py`'s own `len(n) >= 4` convention (independently referenced by checker note W1 for `anchor_rate`). A 3-char floor let a bare `"0.5"` -- a generic RSD/limit value that legitimately recurs for unrelated measurements throughout a 55-page method-validation report -- count as a "distinctive" anchor.
- **`verifier` and `retrieval_recall_at_k` are explicitly-scoped Phase-0 proxies** (documented in code) rather than attempts to force a precise measurement out of data that doesn't support one: the golden fixture is a single post-challenge snapshot (no pre-challenge diff available) and the detector has no explicit top-k retrieval stage yet. Both fall back to `"n/a_phase0"` when genuinely not separable, per the plan's own explicit permission for `verifier`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Matcher over-credited 6 unrelated GT items when scored against the real 28-item ground truth**

- **Found during:** Task 3, while validating `compute_metrics` against the golden fixture + the real `load_eval_set()` (the acceptance criterion requires `end_to_end.tp == 2`)
- **Issue:** The initial `matches()` implementation (Task 1) concatenated `evidence + title + detail` (per the plan's literal `finding_text()` spec) and used a 3-char numeric-token floor (per the plan's literal regex). Against synthetic Task-1 test fixtures this worked correctly, but scored against the real 31-finding golden report and the real 28-item ground truth, it produced `tp=8` instead of `2`: GT items `A-07` (anchor `"0.5%"`), `A-08` (`"specification level"`), `A-09` (`"<1226>"`), `B-08` (`"Any Unspecified Impurity"`), `C-06` (`"Absorptivity Factor"`), and `C-07` (`"entire verification study"`) all false-matched. Root cause: these anchors' distinctive tokens (a bare short number, or common domain vocabulary like "Absorptivity Factor") legitimately recur in the *title/detail* narrative prose of *other* findings discussing the same general topic from a different angle -- concatenating those fields into the search text credited "discusses the same topic" as "matches this specific claim".
- **Fix:** `matches()` now checks `fault["evidence"]` only (dropping title/detail from the anchor-matching codepath specifically, while `finding_text()` itself is left unchanged as a separately-tested, general-purpose 3-field utility other callers may still want), and the numeric-token regex floor was raised from `{2,}` (3-char minimum) to `{3,}` (4-char minimum), excluding bare short numbers like `"0.5"` while keeping both real pinned anchors (`"11477"`, `"0.15"`) matchable.
- **Files modified:** `src/evals/match.py`, `tests/evals/test_match.py` (3 regression tests added)
- **Verification:** `compute_metrics(golden_report(), load_eval_set(), "mvr1381")` now returns `end_to_end.tp == 2`, `end_to_end.fn == 26`, `end_to_end.recall == 0.071...` (matches `2/28` to within `1e-6`), matched GT ids are exactly `{"C-01", "C-02"}`. Full `tests/evals/` suite (54 tests) passes; `ruff check` clean.
- **Committed in:** `9b4e95e` (Task 3 commit, alongside the new metrics.py/test_metrics.py this fix was discovered while building)
