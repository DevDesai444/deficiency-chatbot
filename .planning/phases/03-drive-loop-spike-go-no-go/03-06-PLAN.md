<objective>
Close the phase's most dangerous seam. The agent expresses span-IDs as **strings** — `[doc_id:start:end]` is the only form any tool renders (`get_section.py:48`, `read_guideline.py:72`, `search_corpus.py:73`), and D-GRAN's "cite IDs you can SEE" means a string is the only form the model can honestly produce. But `emit_finding` needs a full `SpanID` **including a content hash** (`schemas/documents.py:136-139`) that is not in the rendered string. The loop must re-mint it.

Here is why that is not ordinary plumbing. `RetrievalLedger` keys on `(doc_id, start, end)` only and ignores the hash (`ledger.py:17,23,26`), so `was_issued()` passes even on a wrongly-minted span. `emit_finding` then calls `open_span`, which **does** verify the hash (`anchors.py:56-64`), and returns `not_byte_exact` with `half="submission"`.

D-TEL3 pre-registers exactly that signature as **SPAN INVENTION — the model fabricated a quote, grounding-discipline failure, the loop is unreliable.** So a loop-side re-mint bug would present as a model failure and could drive a **wrong NO-GO** on a gate that decides three subsequent phases.

Purpose: make the parse/mint path single, store-correct, and provably round-tripping, and make a loop-side failure categorically distinguishable from a model failure.
Output: `spanref.py` as the one path, distinct loop-side reason codes, and the composition test whose absence would let this ship.
</objective>

**(a) The parse/mint function.** Signature and required behavior:

```python
def parse_span_ref(
    ref: str,
    corpus: CorpusIndex,
    rulebook_cache_dir: str,
    expect: Literal["submission", "rule"],
) -> SpanID | ToolRejected:
    """Resolve a rendered span-ID string into a SpanID, or return a typed rejection (never raise).

    Pitfall 1 -- THE reason this module exists. The ledger keys on (doc_id,start,end) and ignores
    the hash (ledger.py:17), so was_issued() passes even on a wrongly-minted span; open_span then
    fails the hash check (anchors.py:56-64) and emit_finding returns not_byte_exact/half=submission
    -- which D-TEL3 pre-registers as MODEL SPAN INVENTION. A loop-side re-mint bug would therefore
    be diagnosed as a model grounding failure and could drive a WRONG NO-GO. Hence: one path, the
    normalizer_version taken from the store rather than assumed, and DISTINCT loop-side reason
    codes that can never be confused with a gate rejection.

    `expect` is REQUIRED, not inferred: Security Domain V4 forbids resolving against whichever
    store answers first. emit_finding enforces the same separation at :66-75; this mirrors it at
    the loop boundary so a store-crossing reference is caught before it reaches the gate.
    """
```

Implementation requirements, each non-negotiable:
1. Parse with `_SPANREF`; a non-matching string returns `reason_code="span_ref_unparseable"`.
2. Look up `doc_id` **only** in the store named by `expect` — corpus for `submission`, rulebook for `rule`. Never fall through to the other store. A `doc_id` absent from the expected store returns `reason_code="span_ref_unknown_doc"`.
3. Take `normalizer_version` from the store itself — `corpus.cached_entry(doc_id)["normalizer_version"]` for submission spans, the rulebook's own normalized-text record for rule spans. **Never** hardcode `NORMALIZER_VERSION` and never assume both stores share one: assuming it is precisely the bug class this module prevents.
4. Re-mint via `ingest.anchors.mint_span(nt.canonical, start, end, doc_id, nt.normalizer_version)`. Do not construct `SpanID(...)` by hand and do not compute the hash inline — `short_hash` is the integrity mechanism (Security Domain V6: never hand-roll a span comparison).
5. Offsets outside the canonical text return `reason_code="span_ref_out_of_range"`.
6. Never raise. Every failure is a typed `ToolRejected` with a `hint` naming the next call to make, matching every `hint` in `src/tools/` (e.g. `hint="re-open the section with get_section and cite a span-ID from its output"`).
7. **Every loop-side rejection carries `half=""`.** The `half` field is populated by `emit_finding` only; a loop-side parse failure is not a citation-half failure and must never be summed into the D-TEL3 matrix.
