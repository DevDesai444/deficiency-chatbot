<objective>
Make both arms runnable from one CLI and prove the agent path does not lose findings.

**D-LOOP1** requires the loop to ship **behind a flag with the existing `run_detection` path left runnable**, so the baseline and the agent loop execute back-to-back on the same corpus during the spike. *"If the old path is replaced outright, the comparison depends on a frozen number nobody can re-derive at gate time."*

**The flag cannot be an `if` inside `run_detection`.** The signatures are incompatible: `run_detection(doc, sections, groups, ...)` is **per-document** (`pipeline.py:37-39`) and the harness calls it in a per-document loop (`evals/run.py:259-281`), while D-BUD5 mandates a **per-run** budget over a multi-document review. Forcing the flag inside would either smuggle a per-document budget back in — *"2/28 by a different route"* — or corrupt the legacy arm. So: a new entry point plus a new subcommand, with the legacy path untouched.

**D-VER1 is proof-by-test, not assumption.** The existing verify/challenge passes do not run over agent findings, because they can DROP them — `verify.py:120-122` drops on `_concedes_compliance`, and `:136-144` dedups on `(_norm(title)[:60], _norm(section), _norm(table_ref))`, which with `emit_finding`'s `title or "Deficiency"` default collapses every untitled agent finding to one key. A dropped finding would silently depress the recall number the gate is reading, and a legacy filter's failure would be attributed to the loop. CONTEXT.md is explicit: *"If any legacy pass IS retained for tiering metadata, it must be provably non-dropping — assert it in a test, do not assume it."*

Purpose: the gate compares two arms. This is what makes both arms runnable, comparable, and honest about what happens between the emit gate and the report.
Output: the `agent-run` subcommand, the config flag for the API path, additive UI events, and the D-VER1 proof.
</objective>
